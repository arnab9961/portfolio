# D.M. Rafiun Bin Masud — Portfolio

A personal AI-engineering portfolio published at [arnab9961.github.io](https://arnab9961.github.io/). The site is a static-first Next.js export with optional Supabase content management.

## Current Portfolio

The mounted homepage is ordered as follows:

1. Morning — hero, with an at-a-glance strip (current role, previous role, stack, what I am open to)
2. Midday — the work, argued in three chapters. Each chapter is one working principle, one lead story with an interactive illustration, and further evidence rows. Projects, experience and principles are merged here so each appears once.
3. Golden hour — Further out: a sideways strip of five photographs, one per place, running from the windowsill outwards
4. Late — Vlogs and Contact

The page reads as one day. Day is the default light; the lamp cord in the masthead switches the whole site, case studies included, to night.

The current static export emits these case-study routes from source data:

- `/work/marshal/`
- `/work/job-search-dispatch/`
- `/work/dsh-conversation-exporter/`
- `/work/moneyguard/`
- `/work/melbourne-ultimate/`
- `/work/alex/`

## Architecture

- Next.js 16 App Router with React 19.
- Fully static production output through `output: "export"`, written to `out/` with trailing-slash routes.
- Route-owned metadata for the homepage and each case study.
- Static `robots.txt` and `sitemap.xml` generated by `app/robots.js` and `app/sitemap.js`.
- Static case-study pages generated from approved source data.
- No API route, server-side rendering runtime, ISR, middleware or application backend is required to serve the portfolio.

`app/page.jsx` owns the homepage route and metadata. `src/App.jsx` is the client boundary for navigation, motion, contexts and local interactions.

## Content Model

Current public content is maintained in these authoritative files:

- `src/constants/constants.js` — hero, at-a-glance strip, toolbox, Further out and Contact content.
- `src/constants/work.js` — the three work chapters, their lead stories, evidence rows and figure copy.
- `src/constants/caseStudies.js` — case-study routes, metadata and page copy.

Public claims are kept evidence-bounded. Changes should preserve the distinctions between verified work, owner-attested facts, learning material and stated limitations.

## Case Studies

`app/work/[slug]/page.jsx` is the reusable static case-study renderer. `CASE_STUDIES` in `src/constants/caseStudies.js` supplies the approved slugs and content; `generateStaticParams()` emits one route per slug, `dynamicParams = false` prevents unknown slugs from generating content, and each page owns its metadata.

Homepage stories and evidence rows link to case studies through `caseStudyHref`. The sitemap derives the same canonical route set from `CASE_STUDIES`.

## Verification

`scripts/verify-static-output.mjs` checks the built files under `out/`. At a high level, it protects:

- meaningful prerendered homepage and case-study HTML;
- the exact approved case-study route set;
- route metadata, canonical URLs, sitemap and robots output;
- required public assets, including the resume PDF and social/project images;
- evidence-bounded public wording, attribution and stated limitations.

`tests/recruiter-journeys.spec.js` drives the production static export in Chromium. It checks direct loads with JavaScript disabled, navigation and case-study return paths, the résumé and outbound-link boundary, contact-form validation and mailto construction, keyboard order and focus visibility, reduced motion, supported viewport widths, horizontal overflow, and portfolio-owned browser errors. External sites and operating-system mail clients are deliberately not controlled; the gate verifies the outbound action instead.

`npm run verify` runs lint, the production build, static-output verification, and the recruiter-journey browser suite. GitHub Actions runs the same command for pull requests and pushes to `main`.

## Supabase admin and vlogs

The public site works with the fallback content when Supabase is not configured. To enable the admin dashboard and managed vlogs:

1. Create a Supabase project and enable email/password auth.
2. Run the migrations in [`supabase/migrations/`](./supabase/migrations/) in the Supabase SQL editor. The follow-up admin-membership migration is required so RLS can verify the signed-in admin.
3. Create an Auth user, then add its UUID to `public.admin_users`:

```sql
insert into public.admin_users (user_id) values ('AUTH_USER_UUID');
```

4. Add these values to `.env.local` for local development and to Netlify environment variables:

```env
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_KEY
```

The dashboard is available at `/admin/`, and published vlogs are shown on their own `/vlogs/` page rather than in the homepage sections. Only users listed in `admin_users` can read drafts, write profile data, manage vlogs, or upload images. If saving a vlog reports that the account is not an admin, add the signed-in Auth user's UUID to `admin_users`. Never use a service-role key in browser-exposed environment variables.

## Deployment

`next build --webpack` writes the static site to `out/`. Netlify uses [`netlify.toml`](./netlify.toml) to publish that directory with Node 22 LTS. Set the build command to `npm run build` if configuring Netlify manually.
